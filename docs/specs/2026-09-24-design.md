# tg-git-notifications-bot — дизайн

Дата: 2026-09-24
Статус: **решения закрыты, готово к плану реализации**
Автор решений: пользователь (ответы на развилки зафиксированы ниже)

## 1. Задача

Вынести git-часть из `tg-claude-bot` в отдельный микропроект — Telegram-бот только про
код-ревью и уведомления GitLab/GitHub.

**Главный фокус:** не пропустить новое ревью, видеть новые комментарии в своих ревью и
ответы на свои комментарии, и не пинговать коллег руками — каждый ставит себе бота и
вовремя получает уведомления.

**Почему отдельный проект:** ноль зависимости от Anthropic API, минимум требований к
развёртыванию, любой человек поднимает у себя за одну команду.

## 2. Зафиксированные решения

| Развилка | Решение |
|---|---|
| Тенантность | **Multi-user, self-hosted** — один деплой, каждый коллега шлёт `/start` и привязывает свой токен |
| Стек | **Один контейнер + SQLite**, без Postgres/Redis |
| Транспорт событий | **Только polling** (бот за NAT, без публичного домена и TLS) |
| Хостинги в v1 | **GitLab** (self-hosted + .com) и **GitHub** |
| Ввод токена | **Сообщением + автоудаление** бота, проверка через `GET /user`, шифрование Fernet |
| Скоуп слежения | **Только моё** — где я reviewer/assignee/author + треды с моим участием + упоминания |
| Действия из чата | **Да** — ответ в тред, approve, resolve (токен с `api`-scope, не `read_api`) |
| Публичность | **Open-source, RU + EN**, MIT |
| Язык | **Python 3.12** — логика MR/stale переносится из tg-claude-bot, а не пишется заново |
| Доступ к инстансу | **Первый `/start` = админ**, остальные — по одобрению админа (кнопки «Пустить / Отклонить»); опционально env `ALLOWED_USERS` для заранее заданного списка |
| tg-claude-bot | **Оставляем оба** — git-фичи в tg-claude-bot не удаляются и не выключаются |
| Состав v0.1 | Пункты **1–14 + 16** (пинг комментарием в MR); cross-user пинг (п.17) — в v0.2 |

## 3. Что переиспользуется из tg-claude-bot

Логика есть, но копируется не как есть, а переписывается под провайдер-абстракцию:

- `app/bot.py:264-700` — MR/PR notify loops (reviewer + authored), stale-алерты
- `bot.mr_seen` / `bot.mr_status` — схема дедупликации и трекинга состояния
- `app/features/dev.py` — `/mrs`, `/mrm`, `/mrdigest`, пагинация, `_mr_age`
- `app/features/integrations.py` — per-chat токены GitLab/GitHub
- Грабли stale-алертов: `STALE_MR_DAYS` (B62), `STALE_MR_MAX_PER_TICK` (B69),
  `STALE_MR_MAX_DAYS` (B78) — переносим готовые ограничители повторов

**Не переносим:** AI-ревью `/cr`, Claude API, дайджесты не про git, VPN, финансы.

## 4. Подход

### Выбрано: A. Провайдер-абстракция + нормализованный поток событий

Ядро не знает про GitLab/GitHub. `providers/*.py` возвращают одинаковые DTO
(`ReviewItem`, `Thread`, `Note`), `core/diff.py` сравнивает со снапшотом в SQLite и
выдаёт `Event`, `core/delivery.py` решает — слать, склеить, отложить.

Новый хостинг (Gitea/Forgejo) = один файл ~200 строк, ноль правок в ядре.
Тестируется без сети на JSON-фикстурах.

### Отвергнутые варианты

- **B. Порт кода из tg-claude-bot как есть** — быстрее на старте (~день), но
  `_mr_notify_*` уже продублирован построчно для GitLab и GitHub; на комментариях и
  тредах дублирование вырастет втрое.
- **C. Плагины + очередь (Redis/Celery)** — оверинжиниринг против «один контейнер».

### Ключевая идея ядра: модель «чей мяч»

Для каждого MR бот считает, на чьей стороне ход:

- автор ответил в треде → мяч у ревьюера
- ревьюер запросил изменения → мяч у автора
- апрувы собраны, конфликтов нет → мяч у автора на мёрж

`/inbox` показывает только то, где мяч **у тебя**. Это принципиально полезнее, чем
плоский поток «новый коммент» — именно из-за потока люди мьютят бота и пропускают ревью.

## 5. Фичи по релизам

### v0.1 — MVP «не пропустить»

Пункты 1–14 ниже плюс **п.16 из v0.2** (кнопка «Пингануть» комментарием в MR). Нумерация не меняется, чтобы ссылки на пункты оставались стабильными.

1. **`/start` — визард без единой env-переменной**: хост (gitlab.com / свой GitLab /
   GitHub) → кнопка «Подключить» → ForceReply → токен → бот удаляет сообщение с
   токеном → проверка `GET /user` → «Привет, @user, нашёл 7 MR на твоём ревью».
   Fernet-ключ автогенерится при первом старте в volume.
2. **Назначили ревьюером** → пуш. GitLab: `GET /todos` + `merge_requests?reviewer_username=`.
   GitHub: `GET /notifications` + `review-requested:@me`.
3. **Новый комментарий в MR, где я ревьюер** → пуш с текстом и ссылкой-якорем.
4. **Ответ на мой тред / мой комментарий** — главный кейс; цитата исходного + ответ.
5. **Мой тред резолвнули / переоткрыли.**
6. **Упоминание `@me`** в любом MR/issue.
7. **По моим MR**: апрув, request changes, новый комментарий, влит, закрыт, конфликт мёржа.
8. **`/inbox`** — единый список непрочитанного, «✓ прочитано» / «✓ всё». Пуш = уведомление
   + счётчик inbox.
9. **`/mr`** — «На моём ревью» / «Мои MR»: апрувы N/M, открытых тредов K, возраст, CI.
10. **Действия из чата**: 💬 Ответить в тред · ✅ Approve · ✔️ Resolve · ⏰ Snooze · 🔗 Открыть.
11. **Мультиаккаунт**: несколько GitLab-хостов + GitHub одновременно, `/accounts`.
12. **`/settings`**: тумблеры по типам событий, интервал, TZ, язык RU/EN.
13. **Тихие часы + выходные** — копится, выдаётся утром одним дайджестом.
14. **Docker в одну команду** + healthcheck + шаблоны Railway/Fly/Render.

### v0.2 — «не пинговать руками»

15. **Stale-алерт мне**: MR висит на моём ревью ≥ N дней → напоминание, с per-tick лимитом
    и верхней границей повторов (готовые ограничители из B62/B69/B78).
16. **[в v0.1]** **Эскалация по моим MR**: «!42 висит у @ivan 2 дня» + кнопка **«🔔 Пингануть»** → бот
    пишет комментарий-напоминание в MR от твоего имени.
17. **Cross-user пинг**: если коллега в том же инстансе — пинг уходит ему **личным пушем
    в Telegram**, а не публичным комментом. Deep-link `t.me/bot?start=invite_<token>`
    для приглашения команды.
18. **Группировка**: 5 комментариев подряд от одного человека в одном MR = одно
    уведомление «💬 Иван — 5 комментариев», debounce-окно 60 сек.
19. **Фильтры шума**: игнор своих действий, Draft/WIP до снятия черновика, боты
    (renovate/dependabot) — тумблерами. `/mute <project>`.
20. **Дайджесты**: утренний «что на тебе сегодня» + вечерний «что ждёт твоего ответа».
21. **`/watch <ссылка на MR>`** — следить за любым, даже чужим MR.

### v0.3 — команда и метрики

22. **Приоритет по лейблам**: `blocker`/`hotfix` пробивают тихие часы.
23. **Незакрытые треды**: «автор ответил на 3 твоих треда — ждёт резолва».
24. **`/load`** — нагрузка ревьюеров в команде: у кого сколько висит.
25. **`/stats`** — личное: отревьюил за неделю, time-to-first-review, сколько твои MR ждут.
26. **Пятничный отчёт**: «12 ревью, медиана ответа 4ч, 2 MR ты держишь 5 дней».
27. **Draft → Ready** как отдельное событие.
28. **CI-фейл на моей ветке** (тумблер, по умолчанию off — это не про ревью).
29. **`/status`** — самодиагностика: токен жив, последний успешный поллинг, остаток
    rate-limit. **Пуш при протухшем токене** — самая тихая поломка таких ботов.
30. **`/test`** — прислать по образцу каждого типа уведомления.
31. **`/export` / `/import`** конфига — переезд на другой инстанс.

## 6. Стек и структура

Python 3.12 · `python-telegram-bot` (polling) · `httpx` · `aiosqlite` ·
`cryptography` (Fernet) · `PyYAML` (i18n). Ноль внешних сервисов. Образ ~80 МБ.

```
tg-git-notifications-bot/
├── README.md (EN) · README.ru.md
├── Dockerfile · docker-compose.yml · .env.example
├── app/
│   ├── main.py           # старт, хендлеры, фоновые лупы
│   ├── config.py
│   ├── storage/          # aiosqlite + миграции
│   ├── providers/        # base.py (Protocol) · gitlab.py · github.py
│   ├── core/
│   │   ├── poller.py     # два уровня опроса (см. ниже)
│   │   ├── diff.py       # новые заметки/треды/апрувы + расчёт «чей мяч»
│   │   ├── inbox.py      # непрочитанное, snooze
│   │   └── delivery.py   # дедуп, debounce, тихие часы, рендер
│   ├── bot/              # onboarding · inbox_cmds · settings · actions · digest
│   └── i18n/ ru.yml en.yml
└── tests/
```

Правило проекта (как в tg-claude-bot): **ни один файл кода длиннее 1000 строк.**

### Двухуровневый поллинг

- **Дешёвый тик** (каждые N минут, по умолчанию 3): `GET /todos` (GitLab) /
  `GET /notifications` (GitHub) + списки MR по `reviewer_username` и `author_username`
  с `updated_at`.
- **Дорогой тик** (только для MR, у которых `updated_at` изменился с прошлого снапшота):
  `GET /merge_requests/:iid/discussions` → диф по ID заметок → классификация события.

Бюджет: ~60 запросов/час на пользователя на дешёвом тике. Лимиты — GitLab 2000/мин,
GitHub 5000/час. Запас кратный.

### Схема SQLite

- `users` — tg_user_id, chat_id, lang, tz, quiet_from/quiet_to, poll_interval
- `accounts` — user_id, kind (gitlab/github), host, username, token_enc, last_ok_at, last_error
- `watched` — account_id, project_id, iid, role, title, url, updated_at_remote, ball, state
- `seen_notes` — watched_id, note_id, ts (дедуп комментариев)
- `events` — user_id, watched_id, type, payload_json, delivered_at, read_at, snoozed_until
- `mutes` — user_id, scope

## 7. Честная оговорка по «настройке по кнопке»

`TELEGRAM_TOKEN` от @BotFather всё равно нужен в env до старта — получить его по кнопке
неоткуда. Всё остальное (GitLab/GitHub токены, ключ шифрования, настройки) — из чата и
автогенерацией.

Деплой сводится к:

```bash
docker run -d -e TELEGRAM_TOKEN=... -v ./data:/data ghcr.io/isaevdimka/tg-git-notifications-bot
```

## 8. Дефолты, выбранные без отдельного вопроса

- Интервал поллинга: 3 мин по умолчанию, минимум 1 мин, меняется в `/settings`.
- Stale-напоминание по MR на моём ревью: 2 дня, повтор не чаще раза в сутки, лимит 5 на тик, перестаёт через 30 дней (опыт B62/B69/B78).
- Эскалация по моим MR (п.16): кнопка появляется, если мяч у ревьюера больше 24 ч.
- Язык интерфейса: из `language_code` Telegram (ru → RU, иначе EN), меняется в `/settings`.
- Таймзона: спрашивается на последнем шаге `/start` (кнопки популярных + ввод IANA).
- Тихие часы по умолчанию: 22:00–09:00 и выходные — включены, можно выключить.
- CI: GitHub Actions → `ghcr.io/isaevdimka/tg-git-notifications-bot`, образы amd64 + arm64, теги по semver.
- Инструменты: `uv`, `ruff`, `pytest` + `pytest-asyncio`, HTTP-фикстуры через `respx`.
- Токены в логах маскируются; сообщение с токеном удаляется даже если проверка не прошла.

### Сосуществование с tg-claude-bot

Оба бота продолжают работать. Если один человек подключит один и тот же GitLab в оба,
уведомления о назначении ревью придут дважды. Это осознанный выбор автора; в README
нового бота будет абзац «если у вас уже есть tg-claude-bot — выключите `MR_POLL_INTERVAL=0` там».
